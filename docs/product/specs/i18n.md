# Spec: Internationalization (i18n)

Status: approved for v1 (D-001). Backlog items: BMI-040 to BMI-044.

## Problem

Every user-facing string in the app is hard-coded in English (`src/ui/App.vue`, the effect labels in `src/engine/effects.ts`, the error in `src/input/decode.ts`). A second language added after the UI grows would mean hunting strings across every component. Brazilian Portuguese is the second language, and more will follow, so the structure goes in now while there are only a handful of strings.

## Goals

1. The app ships in English (`en`) and Brazilian Portuguese (`pt-BR`) in v1.
2. A visitor whose browser prefers Portuguese sees `pt-BR` on first load without touching anything.
3. A visitor can switch language, and the choice survives a reload.
4. Adding a third language means adding one message file and one line in the locale list. No component changes.
5. A missing translation fails a test, not a user.

## Non-goals

- **Right-to-left languages.** None planned. Use CSS logical properties (`margin-inline-start`, not `margin-left`) so RTL isn't blocked later.
- **A translation platform** (Crowdin, Lokalise, Weblate). Two JSON files in the repo are enough until outside translators show up.
- **Machine translation at runtime.** Every string is written by a person.
- **Translating the README and repo docs.** Not part of this spec.
- **Localized URLs and per-locale SEO pages.** Open question Q-001. The design below leaves room for it.

## Requirements

### R1. Library and structure (BMI-040)

- Use [vue-i18n](https://vue-i18n.intlify.dev/) v11 (the official Vue i18n library from Intlify; 11.4.23 published 2026-11-19), Composition API mode (`legacy: false`). It is the standard choice for Vue 3, handles plurals and number formatting through `Intl`, and needs no ESLint.
- Layout:

  ```
  src/i18n/
    index.ts          createI18n, setLocale(), loadLocale()
    locales.ts        SUPPORTED_LOCALES, DEFAULT_LOCALE, resolveLocale()
    messages/
      en.json         source of truth for keys
      pt-BR.json
  ```

- `en.json` is the schema. The i18n instance is typed with `typeof en`, so `t('a.missing.key')` is a type error under `vue-tsc`.
- `en` is bundled statically and is the fallback locale. Every other locale is loaded with a dynamic `import()` the first time it's needed, so the bundle doesn't grow with each language.
- Keys are grouped by screen area: `app.*`, `toolbar.*`, `effects.<id>.*`, `errors.<code>`, `language.*`.

**Acceptance criteria**

- [ ] `vue-i18n` installed; no other i18n package.
- [ ] `src/i18n/` exists with the layout above.
- [ ] A unit test fails if any locale is missing a key that `en.json` has, has a key `en.json` doesn't, or has an empty string.
- [ ] Using a key that doesn't exist in `en.json` fails `pnpm check`.
- [ ] Production build: `pt-BR` messages are in a separate chunk from the main bundle.

### R2. Locale resolution and switcher (BMI-041)

Resolution order on startup, first match wins:

1. Saved choice in `localStorage` (`locale` key), if it's a supported locale.
2. `navigator.languages`, in order. Exact match first (`pt-BR`), then by base language (`pt`, `pt-PT` → `pt-BR`, since it's the only Portuguese we have).
3. `en`.

`resolveLocale()` is a pure function taking the saved value and the browser list, so it can be unit-tested and a URL-based source can be added in front of it if Q-001 goes that way.

The locale is resolved and its messages loaded **before** `app.mount()`, so a Portuguese visitor never sees an English flash.

On every locale change: update the i18n locale, set `<html lang>`, update `document.title`, save to `localStorage`. Wrap `localStorage` access in `try/catch`; private mode must still work.

Switcher: a `<select>` in the page header listing each language by its own name ("English", "Português (Brasil)"), with an accessible label.

**Acceptance criteria**

- [ ] Browser in `pt-BR`, `pt-PT` or `pt` with no saved choice → UI in Portuguese, `<html lang="pt-BR">`.
- [ ] Browser in any other language → English, `<html lang="en">`.
- [ ] Switching language updates the UI without reload and persists after reload.
- [ ] `localStorage` throwing doesn't break the app.
- [ ] Unit tests cover `resolveLocale()` for each case above.

### R3. Existing UI translated (BMI-042)

- Every string in `src/ui/App.vue` moves to message files.
- Effect labels come from `effects.<id>.label`. `EffectDefinition` loses its `label` field. The key-parity test also checks that every id in `effects` has a label key.
- Strings that are **not** translated: exported file names, keyboard shortcut keys (`B`, `E`, `[`, `]`, same as Photoshop in every locale), console logs, test names.

**Acceptance criteria**

- [ ] No user-visible English literal left in `.vue` templates or in strings shown to the user from `.ts` files.
- [ ] `pt-BR.json` complete and reviewed by Ícaro.

### R4. Errors as codes (BMI-043)

- Code never throws user-facing text. It throws an error carrying a code (for example `decode_failed`), and the UI shows `t('errors.<code>')`.
- The proxy already returns `{ "error": "<code>" }` (`invalid_url`, `forbidden_origin`, `too_large`, …). The frontend maps each proxy code to `errors.<code>`.
- Unknown codes show `errors.unknown`.

**Acceptance criteria**

- [ ] `decodeImage` throws a coded error; the UI shows the translated message.
- [ ] Every code the proxy can return has an `errors.*` key, checked by a unit test that reads the code list from the proxy source.
- [ ] An unknown code renders `errors.unknown`, not the raw code.

### R5. Locale-aware formatting (BMI-044)

- Numbers shown with units or decimals (file sizes such as "4.4 MB", dimensions, angle) go through vue-i18n `n()` / `Intl.NumberFormat`, so `pt-BR` shows `4,4 MB`.
- Plurals use vue-i18n plural syntax, never `count === 1 ? … : …` in code.

**Acceptance criteria**

- [ ] The large-image downscale notice (BMI-015) and any size shown in errors use locale formatting.
- [ ] No manual pluralization in components.

## Process rule (Definition of Done)

From BMI-040 onward, every story that adds or changes UI text includes the `pt-BR` strings. The parity test enforces it.

## Testing

- **Unit (Vitest):** key parity across locales, effect label keys, proxy error code coverage, `resolveLocale()` cases.
- **E2E (Playwright):** the default project runs with `locale: 'en-US'` so existing specs stay stable. One spec runs with `locale: 'pt-BR'` and checks the Portuguese UI and `<html lang>`. One spec switches language and reloads.

## Adding a language later

1. Copy `en.json` to `messages/<code>.json` and translate it.
2. Add the code and its native name to `SUPPORTED_LOCALES`.
3. Run `pnpm test`. The parity test lists anything missing.
